# corpus

Each `cases/<id>/` is a hermetic replay case (spec §18.1–18.2):
`replay.json` (manifest), `inputs/` (sanitised host-store files), `pricing/`
(frozen ccusage responses keyed by staged-transcript content), and
`expected/<impl>/` (outputs of that implementation, generated by
`scripts/goldens.mjs`: the declared output roots, non-empty event streams under
`__events__/`, and `__sandbox__/changes.txt` for other sandbox writes — see
`CASES.md` §"Replay infrastructure"). `__events__/` and `__sandbox__/` are reserved: a manifest may not
select an output under them, and every observed file and stream must be valid UTF-8 (Codex B2-02, B2-03). A sandbox file outside the declared outputs that is not valid UTF-8 skips the scrub-token check; its bytes are hashed
unscrubbed into `changes.txt`, so it cannot alias a scrubbed path. Raw sessions never enter this tree; they stay in a local, untracked raw freeze and are reduced by `scripts/build-case.mjs`.

## Migration registry (B2)

`migrations/<id>/migration.json` — one per spec §14.8 migration (ids and items fixed by
`tokenomics/engine/migrations.mjs` `MIGRATIONS`):

```json
{ "id": "exact-ids", "item": 1, "spec": "§14.8 item 1, §10.2", "summary": "<one sentence>",
  "beforeCases": ["<case>"],
  "declared": { "<case>": { "reason": "<≥ 40 chars>", "changed": ["<path>"], "removed": ["<path>"], "exits": [0] } } }
```

`beforeCases` are the existing cases that show the before-behaviour. `declared` is empty until the
migration lands, and must name at least one case once it has — including every `beforeCases` entry,
unless the optional `beforeCasesWaived: { "<case>": "<≥ 40 chars>" }` says why that case keeps its
baseline. The declared after-content lives at
`migrations/<id>/expected/<case>/<path>` as complete files, so the oracle is a byte comparison.
`removed` and `exits` are optional.

Scrub tokens: the replay scrubs sandbox paths to `<REPO>`, `<HOME>`, `<ROOT>`, `<REPOKEY>`, `<ROOTKEY>` and `<IMPL>`.
A selected output file whose raw content already holds one of them is refused as a replay problem
(`content contains scrub token <T>`), so it can never read as a scrubbed sandbox path.

`node scripts/migrations.mjs check [--only <id>]` replays the corpus in four modes (see
`tokenomics/ENGINE-B1.md` "Migrations (B2)") and exits 1 on any problem:

- `none` — `TOKENOMICS_MIGRATIONS=none`; every case equals its baseline (`expected/49577c7`, or
  `expected/engine` for an approved engine-only case).
- `only:<id>` — per landed migration; each declared case equals baseline + that declared diff, every
  other case its baseline.
- `default` — `TOKENOMICS_MIGRATIONS` **unset**, the engine's genuine default. Always runs; with nothing
  landed every case must equal its baseline.
- `all` — the explicit comma list of landed ids; runs once at least one migration has landed.

`default` and `all` compare every case with the **composition** of its declarations: the baseline, then
each landed migration declaring the case applies its `changed` / `removed` / per-event `exits`, in
registry order. A path or event exit (`exit:<i>`) declared by two migrations is a conflict, reported as
`<case>: <path> is declared by <a> and <b> — needs an interaction declaration` until
`migrations/_interactions/<case>/interaction.json` resolves it (format: `migrations/_interactions/README.md`).
An interaction names at least two landed migrations (at least one declaring the case), a reason of at
least 40 characters, and the paths (and exits) the combination produces, which override the composition.
It may override a declared key only when it names every migration declaring that key
(`interaction overrides <key> owned by <id> without naming it`); it may declare paths no migration
changes. No cumulative output is recorded under `cases/`. A declared path may not be spelled `exit:<i>`:
that namespace is the exit keys'. Any other legal filename, `__proto__`, `constructor` and `toString`
included, is an ordinary path (the harness's file maps are null-prototype).

- `write <id> <case>…` — replays `only:<id>`, stores the files that differ from the baseline under
  `migrations/<id>/expected/<case>/` and updates `changed` / `removed` / `exits` (the run's whole exit
  vector when it differs from the baseline; a stale `exits` is dropped). Write `declared.<case>.reason`
  first; it refuses a case without one. It never writes into `cases/`.
- `show <id>` — prints `git diff --no-index` from the baseline to each declared file, and
  `exits: <baseline> → <declared>`: this is how a declared diff is reviewed.
- `write-interaction <case>` — needs `migrations/_interactions/<case>/interaction.json` with `case`,
  `migrations` and `reason` written first, plus the `changed` / `removed` / `exits` keys to pin. It replays
  `default` and records ONLY the conflicted keys and the keys the hand-written interaction already lists
  (the exit vector when it differs). It refuses, writing nothing, on any other difference (naming each
  key: add it to `changed`/`removed` first), on a key an unnamed migration owns — conflicted keys included
  (`<case>: interaction overrides <key> owned by <id> without naming it`) —, on a listed key the run does
  not change (`<case>: listed key <key> shows no difference in the default run`), on a reason under 40
  characters, or when nothing differs, and never writes into `cases/`.
- `show-interaction <case>` — prints `git diff --no-index` from what the declarations alone give (each
  declarer's after-file, or the baseline) to each interaction file: this is how an interaction is reviewed.

Cumulative bytes are never recorded from the implementation except through such an explicit, reasoned
interaction declaration. Declared and interaction after-files are generated by these commands, **never
hand-edited**, and reviewed with `show` / `show-interaction`.
