# Targeted and failure-state cases

Hand-built synthetic cases (no raw content) for branches real sessions do not reach. Each has an
`assert.json` (`ledgerLines` + `facts` as JSON pointers into the last ledger line; optional `fileFacts` into
a collected JSON file such as a captured stdout or a `cost.json`; `{path, absent: true}` asserts a missing key),
checked by `corpus/cases/targeted.test.mjs`. Every case (targeted or real) is compared against its golden by
`corpus/goldens.test.mjs`: all events exit 0 (a deliberate non-zero exit would be declared as `assert.json` `exits`,
one entry per event; `fault-work-scope-usage` and `cov-work-scope-status` do), and `assert.json` may also carry `textFacts` (`{file, equals|includes}` on a captured non-JSON stdout), the produced file set equals the golden file set, and every file is byte-equal.
All Claude events run with `TOKENOMICS_NO_CCUSAGE=1` (dollars are not under test); Copilot dollars come from the session data.

## Replay infrastructure added with branch closure

- An event's `env` value of `null` unsets that variable (`replay/runner.mjs`), so default-fallback branches such as `env.CLAUDE_PROJECT_DIR ?? process.cwd()` are replayable.
- A manifest `symlinks: [{path, target}]` (path relative to the sandbox root, relative target that stays inside it, may dangle) creates symlinks after the stores (`replay/sandbox.mjs`, validated by `validateManifest`). `{impl}` in an event's `args` and `stdin` expands to the implementation root.
- An event field `via: "symlink"` (Plan 3 Task 10) makes the runner create `<sandbox root>/links/<basename of run>` as a symlink to the implementation's script and spawn the link, as an install with symlinked hooks would (`validateManifest` accepts only `"symlink"`). The link is a sandbox write, so it appears in `__sandbox__/changes.txt`. Used by `before-entry-symlink` (map §3 R8).
- An event flag `captureStderr` (mirrors `captureStdout`) collects the event's scrubbed stderr as `__events__/<i>.stderr`, so a deliberate non-zero exit can be told from a crash. Since Plan 3 Task 4 every non-empty stream is captured anyway (below); the flags now only force the file to exist even when the stream is empty.
- Observation boundary (Plan 3 Task 4, Codex P2-12; records Plan 4 Task 2, Codex P3P-02). In one sentence (the wording `docs/spec.md` §18.2 uses): a replay observes the declared outputs byte-for-byte; every event's stdout/stderr (diagnostics normalised); and the final-state path changes, with content digests, under the sandbox root, excluding `.git` directories, the manifest's `untracked` paths and writes outside the sandbox. It does not observe file modes, mtimes, empty directories or transient writes. In detail:
  - the manifest's `outputs` roots (relative to the repo), as before;
  - every event's stdout and stderr, as `__events__/<i>.stdout` / `__events__/<i>.stderr`, written whenever the stream is non-empty. Default-captured streams pass through `normalizeDiagnostics` (`replay/observe.mjs`) and then the sandbox scrub. An explicit `captureStdout: true` keeps raw (scrubbed, not normalised) stdout, so report-producing goldens are untouched; stderr is always normalised, including under an explicit `captureStderr: true` (no existing explicit-stderr golden changed under normalisation);
  - `__sandbox__/changes.txt`: a final-state path-change summary with content digests (Codex P3-03), one record per file, symlink or collapsed git directory under the sandbox root that differs between the snapshots taken before the first and after the last event, sorted by path (relative to the sandbox root), written only when non-empty. Each record is one JSON array on its own line (`JSON.stringify`, records joined by `\n` with a final `\n`): `["A","<path>","<digest>"]`, `["M","<path>","<old>","<new>"]`, `["D","<path>","<old>"]`. A newline, quote or other control character in a path or link target is escaped, so one entry can never read as two (Codex P3P-02, Reproduction F). Each path and link target is scrubbed as a field before serialisation, so escaping never hides a sandbox path from the scrub. A digest is `f:<sha256-16>` of a file's bytes after the runner's sandbox scrub (valid UTF-8 only; other bytes are hashed raw), so a file quoting the sandbox path digests the same wherever the sandbox lives; `l:<target>` for a symlink, the link text scrubbed like every output (e.g. `<IMPL>/…`; `before-entry-symlink` records `["A","links/telemetry-capture.mjs","l:<IMPL>/hooks/telemetry-capture.mjs"]`) — a target outside the scrubbed roots (sandbox root, repo, home, implementation dir) appears verbatim; `u` for an unreadable entry; `g:<sha256-16>` for a git directory. Excluded: the `outputs` roots (already compared), any `.git` directory, and the manifest's `untracked: [{ "path": "<relative to the sandbox root>", "reason": "<≥ 40 chars>" }]` entries (validated by `validateManifest`; the path must stay inside the sandbox). Any other git directory (one holding `HEAD` and `objects/`, e.g. `repo/tgit`) collapses to one `<dir>/` entry whose `g:` digest hashes a summary from read-only git plumbing (`git --git-dir=<dir>`, with `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, `HOME` = the sandbox home, no inherited `GIT_*`): the `HEAD` symbolic target (`git symbolic-ref -q HEAD`, or `detached`), and for each ref from `git for-each-ref` (loose and packed) its name, `git rev-list --count` and its tip's `git ls-tree -r` lines (mode, type, blob id, path; blob ids are git's own object-format hashes — SHA-1 for the corpus's repos; a SHA-256 repository would digest differently). So a commit that adds a commit to a ref, or changes the tip's tree, a file mode or a ref name, reads as `["M","<dir>/","g:…","g:…"]`; two runs agree because commit ids, dates, messages and authors are not included, given the preconditions below. Not observed in a git directory: commit ids, dates, messages and authors, history beyond the commit count and the tip tree, the index, reflogs, hooks, config and loose files git writes (`COMMIT_EDITMSG`, `FETCH_HEAD`, …). A ref git cannot count or list (e.g. a tag of a blob) contributes `ref <name> unavailable` and the rest of the summary stands; if `git` is unavailable or rejects the directory as a whole, the directory is not collapsed — it is walked as ordinary files, so its contents stay visible (and `changes.txt` may then vary between runs, see below). An unreadable directory reads as `<dir>/` with value `u`.
